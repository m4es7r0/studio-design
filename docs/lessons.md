# Lessons

Symptom → cause → rule. Append after every project; when a lesson changes behaviour, update the
rule or stage reference it names.

1. S-08 did not fit 1080, found at the very end → components were built before any screen → stage 3 layout budget (`stage-03-layout-budget.md`).
2. The custom font could not be used in Figma, found mid-build → the Figma MCP runtime sees only Google Fonts → stage 0 font check and Typography variables with a stand-in (`rules/figma.md`).
3. A cloned variant lost its Name and Value bindings → `clone()` drops property references → re-bind after cloning; `audit.js` `refMismatch`.
4. Variants overlapped inside a set → positions not re-laid after adding variants → `audit.js` `overlappingVariants`.
5. The Unfocused window showed a pink button instead of content → a stray INSTANCE_SWAP property bound the slot → `audit.js` `unusedProps` and `refMismatch`.
6. The «10» tick of a chart was cut → a clipping frame narrower than its text → `audit.js` `clippedText`.
7. Sliders in templates stuck at 25 % → handle position cannot be overridden in an instance → build continuous parts with auto-layout widths (`rules/figma.md`).
8. No button size L in Figma → the 30-variant cap was hit → plan size variants first (`rules/figma.md`).
9. Sample values typed by hand → no shared data → `ds/fixtures/` and `format_fixtures.js`.
10. Work started inside an unrelated repository and borrowed its `node_modules` → no own project container → `new-client.sh` and the client `package.json`.
11. No history of the design folder → it was not a git repository → every client container is one.
12. A proposed font failed the character check only at stage 4 → `font_check.py` ran only at stage 4 and U+202F cuts most Google Cyrillic faces → run it on every proposed face at stage 2; `docs/fonts-cyrillic.md` (`stage-02-direction.md`, `rules/design.md`).
13. The browser check failed at stage 0 → the session was opened at the container root and the browser tool binds to the session's root → a root `.claude/launch.json` in the template and a working-folder check at start (`SKILL.md`, `stage-00-intake.md`).
14. The first directions page drew 11 major review findings → the stage reference did not say what the page must show → the directions-page checklist and the review stop rule (`stage-02-direction.md`).
15. The client's «ок» delivered no data → decision questions and material requests shared one list → Decisions and Materials in `questions.md` (`rules/client.md`, template).
16. The layout budget missed an overflow inside a block → zones spanned the whole column → text zones fit their content, buttons and prices `nowrap` (`stage-03-layout-budget.md`).
17. Whether a face existed in the Figma runtime was known only after the client chose a direction → the Figma font check sat at stage 4 → check every proposed face at stage 2 (`stage-02-direction.md`, `stage-00-intake.md`).
18. A focused field in the error state lost one of its rings → error and focus were both drawn with `outline` → draw them with different properties (`rules/design.md`, `stage-02-direction.md`).

Lessons 19–35 come from one redesign run on a fixed base kit, with two themes and an English UI. The rules they name are not written into the stage references and rules yet: each lesson names the file its rule belongs to.

19. The second (dark) theme lived as a «…Dark» twin of every preview, with literal colour values and a hand-kept dark block in `bundle.css` → `build_harness.py` emits only the first theme, an aliased token resolves on `:root`, and no stage or gate names a theme → themes are a `PROJECT.md` field at stage 0; tokens hold a value per theme, the generator makes a twin per extra theme, and the sweep, the contrast check, the look at every preview and the reviewer cover each theme (`build_harness.py`, `previews_spec.py`, `stage-00-intake.md`).
20. Contrast figures were needed from stage 2 on, and a script written for the project found base-kit failures nobody had listed (a field border at 1.26 : 1) → the rules demand AA and forbid ad hoc checks, but the template has no contrast script → a committed contrast script in the template, beside `sweep.js`: every text and UI pair of every theme, alpha composited, an override file for a direction's tokens; «every required pair meets its minimum» is a gate line of stages 2, 4 and 8 (`rules/design.md`, `stage-04-foundations.md`).
21. `format`, its cases and the previews had to be moved to en-US before stage 2, and the font check still required Cyrillic and ₽ of an English UI → the locale is a stage 4 decision, but stage 2 already prints numbers and dates and the generators default to ru-RU → the locale is a `PROJECT.md` field at stage 0: `format`, `format-cases.json` and the preview language follow it before stage 2 (an existing product's cases are copied from what it prints), and `font_check.py` takes its characters from it (`rules/numbers-and-locale.md`, `stage-00-intake.md`).
22. The «ДС» package was stretched to four key screens at intake; once the direction and the first components were published the owner asked for every screen of the registry (eleven screens, 44 states, two themes) → the package counts 1–2 templates, and «the rest in code by the spec» was agreed at intake, before stage 1 had listed the screens → at stage 1 show the owner the registry's screens and record the stage 6 scope as a named list of screens and states; a redesign that goes on to implementation gets «ДС + экраны» as the recommendation (`stage-01-tz-analysis.md`, `docs/packages.md`).
23. Fixtures and screenshots came from a live shared database where opening an item clears a flag for the whole team, and the desktop app once stopped the preview servers mid-stage → the pipeline expects a brief, not a running product, and has no guard for live data → stage 0 records the guard (a read-only connection, the reads that change shared state and how capture skips them); it is re-checked before every capture or fixture run and after every server restart (`stage-00-intake.md`).
24. Stage 1 questions about an existing product needed facts from its code; the brief's sources described different commits, and independent verifiers corrected 14 of 108 researched claims → stage 1 takes facts only from the brief through `tz-analyst` → in entry mode «redesign» a fact lookup reads the code at one recorded commit, cites file and line, and is checked by an independent agent before it becomes a question (`stage-01-tz-analysis.md`).
25. The owner assembled the final direction from parts of all three, and the combined build needed a second revision before it was accepted → the directions page compares whole directions, and «redesign» plans a single one → every direction decides the same named parts (shell, list, detail view, status signals, icons, tokens) and the page lets each be chosen on its own; a combined build with a click-through audit comes before the reviewer (`stage-02-direction.md`).
26. The accepted direction was a full interactive prototype with its own system page; stage 5 rebuilt its parts as components, and two owner revisions during stage 5 had to be made in both → for a product redesign the stage 2 page grows into a second implementation ahead of stages 3–5 → freeze the prototype at acceptance: later revisions go into components and screens, and each component batch is gated on computed-style parity with it, every difference a recorded decision (`stage-02-direction.md`, `stage-05-components.md`).
27. No reviewer pass came back clean (direction: three passes, a new major in each; library: 5 majors, then 3), no reviewer saw the last fixes, and the owner cut the screens review to one pass to save time → a pass re-reads everything and each fix opens new surface; the stop rule caps the passes and says nothing about the fixes of the last one → agree the passes per stage with the owner at stage 0, verify each last-pass fix by its finding's own repro, and list in the handoff what no reviewer saw again (`stage-00-intake.md`, `stage-02-direction.md`, `stage-08-qa-handoff.md`).
28. The library review, run while screens were being assembled, found no parts for a titled section, a form column and a bare page, and the screens review found five screens that had each built their own → the component registry lists widgets; page-level layout parts show up only when screens are built → take the layout parts from the stage 3 budget sheets into the registry and build them before the last batch; a screen file defines no reusable part (`stage-05-components.md`, `stage-06-screens.md`).
29. Stage 8 found the focus ring cut on most tile stops (345 of 367) and at the edges of scroll containers and rails, and dimmed with an unavailable button → a component's preview card shows focus on a part standing free of any scroll container, and nothing measures the ring before stage 8 → when a component is built, focus it from the keyboard inside its real scroll container and check all four sides of the ring and its 3 : 1; scroll containers get `scroll-padding` (`stage-05-components.md`, `rules/design.md`).
30. 312 measure runs, a 292-page sweep and the stage 8 accessibility figures came from headless runners kept in the session's scratchpad, and every measured page needed a «…Fixed» twin for its fixed-height run → the committed measure takes one page and one size per load in the browser pane, a page carries one set of zone marks, and stage 8 names no accessibility script → the template ships a headless matrix runner (sweep, measure) and an accessibility walk, `previews_spec.py` makes the fixed-height twin, and run output goes to a generated file with totals in `progress.md` (`rules/design.md`, `stage-06-screens.md`, `stage-08-qa-handoff.md`).
31. The acceptance carried 32 open questions, 19 decision rows marked «to confirm at the stage 8 checkpoint» and five plan questions, all answered with one sentence; the few asked on the spot were answered the same day → stages 3–7 have no checkpoint, so every studio choice made after the stage 2 acceptance waited for the last one → each stage report carries its own «to confirm» list, a choice that changes what the owner sees is asked then, and the last checkpoint lists only what is still open (`rules/client.md`, `SKILL.md`).
32. The UI spec and the implementation plan, drafted while screens were still being built, were re-synchronised after the final build and again after late owner answers, and three screens still await a line-by-line check → the documents described screens that did not exist yet → implementation documents follow the stage 6 gate; an early draft covers only screens that passed their gate and gets one scheduled sync after the last owner answer (`stage-08-qa-handoff.md`).
33. After a late owner answer moved a state to another screen, the handoff note, the code mapping and two brief files still named the old page (one old name was still found at acceptance), and the handoff kept a «not republished yet» note after the final publish → the workflow applying the answer changed only the design sources; no step owns the documents that quote page names, counts and version ids → a late change lists every document that quotes what it renames, and after the last publish the session greps the handoff and the brief for them (`stage-08-qa-handoff.md`).
34. The session could not look at a published page: the built-in browser was not signed in to the artifact host → stage 0 checks that the artifact type exists, not that the session can open the page → verify each publish by reading the artifact back, note in `progress.md` what only the open page can show (the files the type compiles itself), and ask the owner to look (`rules/artifact.md`, `stage-00-intake.md`).
35. A scripted rewrite that cut a handoff document «from a marker to the next heading» removed two subsections, and the file had no committed version to restore from → handoff files are written late in stage 8 and committed only at the gate, and the rewrite matched by position, not by text → commit each handoff file as soon as its first draft exists; a scripted edit replaces an exact string and checks that it matched once (`stage-08-qa-handoff.md`).

Lessons 36–44 come from the implementation phase of the same run: the hand-off was built by parallel coding agents under part reviews, then audited on «after» screenshots. As above, each lesson names the file its rule belongs to.

36. The code mapping and the «Code mapping» sections of 21 component READMEs disagreed with the built app at the end, and the mapping was re-aligned by hand three times → class strings were written before the build, and every review fix changed them in code only → the mapping is an estimate until the build: one pass after it rewrites the mapping from the code with file and line, component READMEs carry no class lists, and a fix brief names the mapping rows it changes (`stage-08-qa-handoff.md`, `stage-05-components.md`).
37. Four defects reached the end although every part had been reviewed with adversarial verification: a link running out of a 400 px pane, table columns cut with no way to reach them, a select list flipping over the fields above it, a square focus box on a heading → reviewers read code and compared class strings; nothing rendered real data at real widths until the «after» screenshots → after each built part the session measures its screens in a browser on real data (a box inside its parent, scroll width against client width, a list under its trigger, the focus ring's four sides) (`stage-08-qa-handoff.md`).
38. At the width the owner had called «works, not designed» tables lost columns and header actions left the frame → the spec had one word for that width and no check → for each undesigned width the spec lists what must stay reachable (every action, every column by scroll, a readable title), and the capture and the measure run include it (`stage-03-layout-budget.md`, `stage-08-qa-handoff.md`).
39. Three spec rows contradicted the samples and were found only by comparing screenshots with previews (a count line shown only for a partial group, a fixed basis that squeezed a link, a list that should hang under its field) → the spec paraphrased READMEs and screens → a spec row cites the sample's file and line, the sample wins where both exist, and the row is corrected in the change that finds the difference (`stage-08-qa-handoff.md`).
40. A rule about which third-party popup counts as open passed its unit tests and two reviews and failed in the first browser scenario: a tooltip that was fading swallowed a key press → the unit tests encoded the author's model of the kit's markup, not the kit's → a rule that reads a library's DOM states gets one browser-level test when it is written, even when the end-to-end suite is scheduled last (`stage-08-qa-handoff.md`).
41. «Labels with IDs use tabular figures» made every hyphen of a domain label as wide as a figure, and a dark overlay had no visible edge over dark content → both tokens were accepted on fixtures (numeric IDs, light pictures) → a font feature and an elevation token are tried on the real strings and on the darkest real content before they become rules (`stage-04-foundations.md`, `rules/design.md`).
42. The kit's generated files could not be edited, and several looks needed what its wrappers do not pass on (a popup's collision rule, an overlay's motion, an unavailable button) → the hand-off mapped looks to kit parts without reading which props each wrapper forwards → for every component the hand-off lists what the look needs from the kit and whether the installed wrapper passes it; the rest goes into one named overrides block or a recorded workaround (`stage-05-components.md`, `stage-08-qa-handoff.md`).
43. A long parallel run lost its agents' answers when the machine slept, and later every agent of a wave was cut twice by a server overload → results lived only in the agents' final answers → each agent writes its report file before it answers, the runner can resume by verifying from reports instead of rebuilding, and the session asks to keep the machine awake before a long run (`SKILL.md`).
44. Parallel implementers and reviews with two skeptics per finding cost several million tokens a run before the owner asked for a cheaper model, and a read the plan required on live data was refused by the session's permission layer → the model per role, a budget and the plan's guarded commands were not settled before the run → an implementation run starts by agreeing the model per role (the cheaper one for documents and specified tests) and a budget for optional reviews, and by executing each guarded command once in the executing session, recording who runs it when the session cannot (`stage-00-intake.md`, `rules/client.md`).
